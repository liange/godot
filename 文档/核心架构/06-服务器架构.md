# 06 服务器架构

## 职责定位

服务器（Server）是 Godot 处理计算密集、可线程化子系统的统一范式：渲染、物理、音频、文本、导航、显示、XR、相机。每个服务器是一个**虚接口**（位于 `servers/`），有默认实现与可替换后端；场景层 `scene/` 的节点是服务器的「前端」，把服务器返回的不透明句柄 RID 包装进节点树。服务器通过 `*_wrap_mt` 包裹实现线程安全（命令队列模式），让前端可在主线程安全调用而后端在独立线程执行。这是 Godot「前后端分离」与「单线程友好 API、多线程后端」设计的核心。

## 服务器模式总论

每个服务器遵循统一的三层结构：

```
前端节点 (scene/)          服务器虚接口 (servers/)         后端实现
  Node3D ──┐               RenderingServer ──┬── RenderingServerDefault
  Sprite ──┤  调用          PhysicsServer3D ──┼── PhysicsServer3DWrapMT ── PhysicsServer3D (godot_physics/jolt)
  ...      │  (持 RID)                         │                            └── GDExtension 后端
           │                                    ├── RenderingServerDummy
           ▼                                    └── ...
   RID 句柄由服务器创建并返回，前端保存 RID，后续操作经 RID 寻址
```

- **虚接口**：纯虚 `Object` 子类，定义 `*_create`/`*_set_*`/`*_get_*` 等方法，返回或接收 `RID`。经 `GDREGISTER_VIRTUAL_CLASS` 注册（见 [03](03-类型系统与反射.md)），可被脚本/GDExtension 调用。
- **RID（Resource ID）**：服务器对象的不透明句柄，本质是 ` RID_Owner<T>` 分配的 ID。前端只持有 RID，不直接访问后端对象，保证封装与线程安全。
- **默认实现 + 可替换后端**：服务器有默认实现，同时通过 Manager 机制允许多后端竞争（如物理的 godot_physics vs jolt），通过 Extension 机制允许 GDExtension 提供后端。
- **单例**：每个服务器是 `Engine` 单例，经 `Engine::add_singleton` 注册，全局 `RenderingServer::get_singleton()` 等访问。

## MT 包裹：命令队列模式

`servers/server_wrap_mt_common.h` 用宏为每个服务器方法生成线程安全的包装。以 `PhysicsServer3DWrapMT`（`physics_server_3d_wrap_mt.h:63 : public PhysicsServer3D`）为例：

```cpp
class PhysicsServer3DWrapMT : public PhysicsServer3D {
    mutable CommandQueueMT command_queue;   // 命令队列
    PhysicsServer3D *physics_server_3d;     // 真实后端
    // 每个方法用宏生成:
    FUNC2(body_set_state_sync_callback, RID, const Callable &);
};
```

宏变体（`server_wrap_mt_common.h`）按「是否返回值」「是否同步」「是否 const」分类：

| 宏后缀 | 行为 |
|--------|------|
| `FUNC*`（无 R/S） | 入队异步执行，立即返回 |
| `FUNC*R`（带 R） | `push_and_ret`：入队并阻塞等待返回值 |
| `FUNC*S`（带 S） | `push_and_sync`：入队并同步等待完成 |
| `FUNC*C`（const） | const 方法版本 |
| `FUNCRID` / `FUNCRIDSPLIT` | RID 创建：分配 RID 立即返回，初始化入队或同步 |

每个宏展开为类似（`server_wrap_mt_common.h:90` 的 `FUNC0`）：

```cpp
virtual void m_type() override {
    WRITE_ACTION
    if (ASYNC_COND_PUSH) {                                  // 后端在独立线程
        command_queue.push(server_name, &ServerName::m_type);  // 入队
    } else {                                                // 单线程模式
        command_queue.flush_if_pending();
        server_name->m_type();                              // 直接调用
    }
}
```

- `ASYNC_COND_PUSH`：判断是否启用多线程（`create_thread`）。启用时入队，后端线程在 `step`/`sync` 时 flush 队列；禁用时退化为直接调用。
- 带返回值的 `FUNC*R` 用 `push_and_ret`，会同步等待后端线程执行完毕返回结果--这在主线程调用时形成同步点，`MAIN_THREAD_SYNC_CHECK`（`server_wrap_mt_common.h:36`）在 DEBUG 下警告每帧同步（性能杀手）。
- `FUNCRIDSPLIT`（`server_wrap_mt_common.h:58`）：先 `allocate` 一个 RID 立即返回（前端可立即持有），`initialize` 入队异步执行，避免创建资源的同步等待。

这套宏让物理服务器的数百个方法都被自动包装，无需手写。`CommandQueueMT`（`core/templates/command_queue_mt.h`）是带类型擦除的命令队列，存储方法指针+参数，后端线程 `flush` 时顺序执行。

## RenderingServer 渲染服务器

`RenderingServer`（`servers/rendering/rendering_server.h:64 : public Object`）是渲染的统一接口，覆盖 2D（canvas）与 3D（scene）。

### 接口概要（`rendering_server.h`）

- **纹理**：`texture_2d_create`/`texture_3d_create`/`texture_rd_create`（`:110-156`），含占位纹理、原生句柄导入。
- **材质/着色器**：`material_create`/`material_create_from_shader`（`:177-178`）。
- **网格**：`mesh_create`/`mesh_create_from_surfaces`（`:193-194`），surface 取顶点/属性/索引 buffer 的 RD RID。
- **光照**：`light_*`、`lightmap_create`（`:419`）。
- **视口**：`viewport_create`（`:541`）、`viewport_get_render_target`/`viewport_get_texture`（`:566-567`）、`viewport_find_from_screen_attachment`（`:621`）。
- **场景实例**：`instance_create`/`instance_create2`（`:729-731`），把 mesh/light 等基资源实例化到 scenario。
- **2D canvas**：`canvas_create`/`canvas_texture_create`/`canvas_item_create`/`canvas_light_create`/`canvas_light_occluder_create`（`:784-927`）。
- **帧驱动**：`draw(swap_buffers, frame_step)`（`:971`）、`sync()`（`:972`），由 `Main::iteration` 调用（见 [01](01-启动与主循环.md)）。

### RenderingServerDefault 与线程模型

`RenderingServerDefault`（`rendering_server_default.h:47 : public RenderingServer`）是默认实现，其线程模型比通用 MT 宏更定制化：

- `server_thread`（`:139` 附近）：渲染线程 ID。`create_thread`（`:85`）决定是否启用独立线程。
- 资源创建（`*_create`，如 `rendering_server_default.h:137` 的宏）：若调用线程即渲染线程，或 rasterizer 支持 `can_create_resources_async()`，则直接创建；否则入队到渲染线程。这避免不必要同步，因为现代 RD（Vulkan）多数资源可异步创建。
- `command_queue`（`:1197/1226`）：`free(RID)`、`call_on_render_thread(Callable)` 等入队。
- 帧调度：`sync()` 同步上一帧绘制完成，`draw()` 提交本帧。在 `Main::iteration` 中先 `sync` 后 `draw`（见 [01](01-启动与主循环.md)）。

### RendererCompositor 渲染合成器

`RendererCompositor`（`servers/rendering/renderer_compositor.h:52`）是渲染后端的顶层抽象：

```cpp
class RendererCompositor {
    static RendererCompositor *(*_create_func)();   // 平台/驱动注册的创建函数
    static RendererCompositor *create();
    virtual RendererCanvasRender *get_canvas() = 0;  // 2D 渲染器
    virtual RendererSceneRender *get_scene() = 0;    // 3D 渲染器
    virtual void initialize() = 0;
    virtual void begin_frame(double frame_step) = 0;
    virtual void end_frame(bool p_present) = 0;
    virtual bool can_create_resources_async() const = 0;
};
```

- `_create_func` 由具体后端（`RendererRD`/`RendererCanvasRenderRD` 等）在初始化时设置，`create()` 工厂生成实例。
- 划分 2D（`RendererCanvasRender`）与 3D（`RendererSceneRender`）两条路径，各自有 cull（剔除）与 render（渲染）。
- `renderer_rd/` 目录是 Vulkan/RD 实现：基于 `RenderingDevice`，是 4.x 的主力渲染器（Forward+/Mobile）。
- GLE3 渲染器在 `drivers/gl`，Metal/D3D12 经各自的 context/driver driver。

### RenderingDevice (RD) 设备抽象

`RenderingDevice`（`rendering_device.h:67 : public RenderingDeviceCommons`）是现代图形 API 的抽象层，提供类 Vulkan 的资源模型：

- 资源创建：`texture_create`/`texture_create_shared`（`:463-466`）、`framebuffer_create`（`:709`）、`vertex_buffer_create`/`index_buffer_create`（`:867/876`）、`uniform_buffer_create`/`storage_buffer_create`（`:1051/1056`）。
- 命令录制：`draw_list_begin`（`:1545`）录制绘制命令，`compute_list_begin`（`:1674`）录制计算命令，支持 split（多命令列表并行）。
- 三层抽象：`RenderingContextDriver`（上下文，如 Vulkan Instance）-> `RenderingDeviceDriver`（`RDD`，逻辑设备/队列）-> `RenderingDevice`（高层资源管理，`rendering_device_graph` 构建提交图）。
- `rendering_device_graph.h`：命令图，延迟提交、自动屏障、减少同步开销。
- 单例 `RenderingDevice::get_singleton()`，供渲染器与 GDExtension（计算着色器、自定义渲染）共用。

这套分层让 Godot 可在 Vulkan、Metal（经 MoltenVK 或原生 metal-cpp）、D3D12（directx_headers）等后端上运行，上层渲染器代码不感知具体 API。

### 渲染存储与剔除

- `storage/`：`RendererTextureStorage`/`RendererMeshStorage`/`RendererMaterialStorage`/`RendererLightStorage` 等，按资源类型组织后端数据，由 RID 索引。`rendering_server_globals.h` 的 `RSG::*` 全局指针统一访问。
- `renderer_scene_cull.h/.cpp`：3D 场景剔除（视锥、遮挡、BVH），生成可见实例列表交 `RendererSceneRender`。
- `renderer_canvas_cull.h/.cpp`：2D canvas 剔除与排序。
- `renderer_scene_occlusion_cull.h`：遮挡剔除（含 BVH 与栅格化方案）。
- 着色器：`shader_compiler.h`/`shader_language.h`/`shader_preprocessor.h` 编译 Godot 着色器语言为后端 SPIR-V，`rendering_shader_container.h` 管理编译产物。

### 前端节点对应

| 前端节点（scene/） | RenderingServer 资源 |
|------|------|
| `Sprite2D`/`Control`（经 `CanvasItem`） | canvas item RID |
| `CanvasLayer` | canvas RID |
| `Node3D` | instance RID（在 scenario 中） |
| `MeshInstance3D` | mesh RID + instance |
| `Camera3D` | viewport camera |
| `DirectionalLight3D`/`OmniLight3D` | light RID |
| `World3D` | scenario RID |
| `Viewport`/`Window` | viewport RID |

节点通过 `RenderingServer::get_singleton()` 调用，持有 RID；`queue_redraw` 标记 canvas item 需重绘（见 [04](04-节点与场景树.md)）。资源（`Texture2D`/`Mesh`/`Material`）经 `Resource::get_rid` 桥接（见 [05](05-资源系统.md)）。

## PhysicsServer 物理服务器

### 接口（`physics_server_3d.h:51`）

`PhysicsServer3D : public Object`，纯虚：

- **空间**：`space_create`（`:90`），每个 `World3D` 一个 space。
- **形状**：`world_boundary_shape_create`/`box_shape_create`/... （`:66` 起）。
- **区域**：`area_create`/`area_set_space`/`area_get_space`/`area_get_shape`（`:110-120`），触发器与检测区。
- **刚体**：`body_create`/`body_set_state`/`body_get_space`/`body_get_shape`（`:154-167`），`body_set_state_sync_callback` 用于回写变换到 Node3D。
- **步进**：`step(real_t)`（`:384`）推进物理，`sync()`（`:385`）同步、`flush_queries()`（`:386`）刷新区域/碰撞查询。
- **直接状态**：`PhysicsDirectBodyState3D`/`PhysicsDirectSpaceState3D` 供脚本直接查询。

`step`/`sync`/`flush_queries` 的调用时序见 [01 启动与主循环](01-启动与主循环.md) 的 `iteration`：物理循环内 `sync` -> `flush_queries` -> 前端 `physics_process`（节点读物理结果）-> `step`。

### MT 包裹

`PhysicsServer3DWrapMT`（`physics_server_3d_wrap_mt.h:63`）用 `server_wrap_mt_common.h` 宏包装真实后端（`physics_server_3d` 指针）。`PhysicsServer3DWrapMT(PhysicsServer3D*, bool create_thread)`（`:417`）：`create_thread=true` 时后端在独立线程运行，命令队列异步；`=false` 退化为单线程直接调用。`step`/`sync`/`flush_queries` 是帧同步点，后端线程在此时 flush 队列并执行。

`PhysicsServer2DWrapMT`（`servers/physics_2d/`）结构相同。

### Manager 后端选择

`PhysicsServer3DManager`（`physics_server_3d_manager.h:37 : public Object`）：

- `register_server(name, create_callback)`（`:76`）：注册一个后端（如 godot_physics、jolt）。
- `new_server(name)`（`:82`）：实例化指定后端。
- `initialize_server()`/`initialize_server_manager()`（`:84/87`）：启动时由 `Main::setup2` 调用（`main.cpp:3121`）。
- 默认后端由项目设置 `physics/3d/physics_engine` 决定（默认 godot_physics，可选 jolt）。

### Extension 后端

`PhysicsServer3DExtension`（`physics_server_3d_extension.h`）让 GDExtension/C++ 提供物理后端：继承并实现 `step`/`body_create` 等虚方法，注册为 Manager 后端。`PhysicsServer3DRenderingServerHandler`（`physics_server_3d_rendering_server_handler.h`）桥接物理与渲染（如软体可视化、调试绘制）。

### 前端节点对应

| 前端节点 | PhysicsServer 资源 |
|------|------|
| `World3D`/`World2D` | space RID |
| `StaticBody3D`/`RigidBody3D`/`CharacterBody3D` | body RID |
| `Area3D` | area RID |
| `CollisionShape3D` | shape RID（附加到父 body/area） |

`CollisionObject3D` 是 body/area 的共同基类，`body_set_state_sync_callback` 把物理变换回写到 `Node3D`。

## ASCII：服务器三层架构

```
   场景层前端节点 (scene/)                     主线程
     Node3D / Sprite2D / RigidBody3D / ...
        │ 持有 RID, 调用 *_create / *_set_*
        ▼
   服务器虚接口 (servers/)                     单例 API（线程安全外观）
     RenderingServer / PhysicsServer3D / ...
        │
        ├─────────── MT 包裹 (*_wrap_mt) ──────────┐
        │   FUNC*R/S: command_queue.push_and_ret   │ 后端线程
        │   FUNC*  : command_queue.push            │ (create_thread)
        │   FUNCRID: allocate RID 立即返回          │
        │              initialize 入队              │
        ├──────────────────────────────────────────┘
        ▼
   后端实现 (servers/ + modules/)
     RenderingServerDefault ──► RendererCompositor
     │                              ├─ RendererSceneRender (3D) ── RenderingDevice
     │                              └─ RendererCanvasRender (2D)   (Vulkan/Metal/D3D12)
     PhysicsServer3DWrapMT ──► godot_physics / jolt (modules/)
     AudioServer ──► AudioDriver (platform/)
     TextServerManager ──► text_server_adv / fb (modules/)
     NavigationServer3DManager ──► navigation_3d (modules/)
   ▲
   │ step / sync / flush_queries / draw / update
   │ 由 Main::iteration() 在帧循环内调度 (见 01)
```

## 与其他子系统关系

- **主循环**：`Main::iteration` 调度所有服务器的 `step`/`sync`/`draw`/`update`，见 [01 启动与主循环](01-启动与主循环.md)。
- **对象系统**：服务器是 `Object` 单例，经 `ClassDB` 注册，`CommandQueueMT`/`MessageQueue` 提供线程间调用，见 [02 对象系统](02-对象系统.md)。
- **类型系统**：服务器接口用 `GDREGISTER_VIRTUAL_CLASS`，Extension 后端经 `ObjectGDExtension` 接入，见 [03 类型系统与反射](03-类型系统与反射.md)。
- **节点/场景树**：前端节点是服务器 RID 的包装，`queue_redraw`/`_physics_process` 桥接，见 [04 节点与场景树](04-节点与场景树.md)。
- **资源系统**：`Resource::get_rid` 把服务器资源封装为可序列化资源，资源析构释放 RID，见 [05 资源系统](05-资源系统.md)。
- **OS/平台**：`DisplayServer`/`AudioDriver` 是平台后端，渲染 context 经平台窗口系统，见 [07 OS 与平台抽象](07-OS与平台抽象.md)。
- **模块/扩展**：物理、文本、导航、XR 的实际后端多在 `modules/`，GDExtension 可经 Extension 接口提供后端，见 [10 模块与构建](10-模块与构建.md)。
